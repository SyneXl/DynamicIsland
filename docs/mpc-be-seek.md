# Перемотка MPC-BE

## Причина и решение

В проверенном MPC-BE x64 1.9.0 включённая интеграция с Windows публикует
название, тип медиа и кнопки воспроизведения, но не системную шкалу времени.
Поэтому одного GSMTC недостаточно для времени и перемотки в острове.

| До | После |
| --- | --- |
| `–:––`, неактивная полоса при нулевой системной шкале | Текущее и оставшееся время из native-контрола MPC-BE |
| Перемотка только через системную медиасессию | Для MPC-BE без системной шкалы — его собственный seek-bar |
| Один идентификатор приложения для нескольких экземпляров | Дополнительное сопоставление заголовка, файла и PID |

`MpcTimeline.cs` находит окно выбранного трека, проверяет процесс и считывает
текст штатного контрола времени (`10016 → 10627`). При отпускании полосы
перемотки он отправляет ограниченную по времени пару `WM_LBUTTONDOWN/UP`
штатному seek-bar (`10017`). Положение рассчитывается по геометрии контрола,
DPI и светлой/тёмной теме. Затем адаптер читает реальную позицию плеера;
одна успешная отправка сообщения не считается успешной перемоткой.

Это работает и со скрытыми полноэкранными панелями. Курсор не перемещается,
плеер не активируется. Воспроизведение на паузе остаётся на паузе.
Обычный путь GSMTC у других приложений и существующий Telegram fallback
сохраняются. Если MPC-BE начнёт отдавать системную шкалу, приоритет останется
у GSMTC.

## Условия и ограничения

- В MPC-BE должна быть включена его встроенная интеграция с медиасистемой
  Windows: она нужна для выбора трека и состояния воспроизведения.
- Расширения, web server, `/slave`, инъекции и изменение настроек плеера не
  используются. Тема читается из portable ini либо реестра **только для чтения**.
- Опрос идёт в фоне с существующим интервалом 250 мс при воспроизведении
  и 1000 мс на паузе; привязка к HWND кэшируется. Win32-вызовы ограничены
  тайм-аутами, WPF-поток не ждёт native-перемотку.
- Поддержаны `mpc-be64.exe` и `mpc-be.exe`, обычный и оставшийся отсчёт,
  часы и миллисекунды. Режим счётчика кадров, live без длительности,
  нестандартный несовпадающий заголовок или несколько одинаковых заголовков
  дают неактивную шкалу вместо перемотки произвольного окна.
- Плеер с более высоким уровнем привилегий может блокировать межпроцессные
  сообщения. Адаптер не повышает привилегии и не обходит эту границу.
- Использованы штатные контролы MPC-BE 1.9.0. При изменении их идентификаторов
  или устройства в будущей версии потребуется повторная проверка.

## Проверка

`dotnet run --project Tests/DynamicIsland.Tests.csproj -c Release`:
73 проверки, включая парсинг, координаты при разных DPI, очистку состояния,
передачу времени в модель и обе временные подписи WPF.

Отдельная portable-копия установленного MPC-BE проверена на собственных
120-секундных AVI/WAV. Для изоляции от пользовательской медиасессии копия
названа `mpc-be.exe`. В каждом сценарии проверены native-переходы на
30, 90, 12 секунд и перемотка через настоящий `MediaService` на 60 секунд:

- видео в окне, тёмная тема;
- видео на паузе во весь экран со скрытыми панелями, тёмная тема;
- аудио в окне и во весь экран: перемотка работает, видео не определяется;
- светлая тема в окне и на паузе во весь экран со скрытыми панелями.

Отрицательные проверки: чужой трек не получает перемотку; второй экземпляр
с тем же приложением не превращает аудиофайл в видео; пауза сохраняется.
Пользовательский MPC-BE проверен только чтением времени — его файл,
позиция воспроизведения и настройки тестами не менялись.
